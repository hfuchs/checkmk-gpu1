# CheckMK Local Checks — Developer Manual

## Overview

CheckMK local checks allow you to create custom monitoring services by writing scripts that run **directly on the monitored host** (where the data is collected). This eliminates the need to write Python check plugins and gives you full freedom to choose any scripting language supported by the target system.

---

## 1. The Output Format

Every line produced by a local check script must follow this 4-part output format:

```
<STATE> "<SERVICE_NAME>" <METRICS> <DETAILS TEXT>
```

| Field | Description | Example |
|---|---|---|
| **STATE** | `0` = OK, `1` = WARN, `2` = CRIT, `3` = UNKNOWN, `P` = dynamically calculated state from thresholds | `0` |
| **SERVICE_NAME** | Shown in CheckMK, must be in double quotes | `"My service"` |
| **METRICS** | Value(s) for graphing, or `-` for no metrics | `myvalue=73;65;75` |
| **DETAILS TEXT** | Free-form state detail text (the “Summary” field), may contain spaces | `"Some output text which may contain spaces"` |

**Important:**
- Up to CheckMK 2.4.0p4: exactly one space (ASCII 0x20) must separate the four parts. Starting with 2.4.0p5, multiple spaces are allowed and parse errors produce a CRIT service with diagnostics messages.
- Each output line becomes its own service in CheckMK. No unescaped newlines are allowed in the body of your script's output text.

---

## 2. Writing Simple Local Checks

### 2.1 Bash Example

```bash
#!/bin/bash
echo "0 \"My 1st service\" - This static service is always OK"
```

Note the escaped double quotes around the service name (`\"...\"`) needed so the shell passes them literally.

### 2.2 Windows Batch Example

```bat
@echo off
echo 0 "My 1st service" - This static service is always OK
```

### 2.3 Multiple Output Lines

You can produce any number of output lines — each becomes its own service:

```bash
#!/bin/bash
echo '0 "Service A" value=42 OK'
echo '1 "Service B" value=55 WARNING'
```

### 2.4 Service Name Restrictions

| Edition | Restrictions |
|---|---|
| **Nagios Core** (CheckMK Community) | Forbidden: `` `;~!$%^&*|\'"<>?,()= `` — they are simply removed |
| **CMC** (Commercial editions) | No `;` in names; `$` only displays correctly if escaped (`\$`). Single quotes in names cause the service to be undiscoverable! |

## 3. Metrics

### 3.1 Shortest Syntax

```
metricname=value
```

### 3.2 Full Syntax

```
metricname=value;warn;crit;min;max
```

| Field | Description |
|---|---|
| `value` | Current value |
| `warn` | Warn threshold (upper) |
| `crit` | Crit threshold (upper) |
| `min` | Minimum value (graph range) |
| `max` | Maximum value (graph range) |

**Example:** `count=73;80;90;0;100`

Values that are not required can be left empty (field ends with nothing, or is omitted at the end).

```
count=42;;;0     ← warn, crit empty
```

> **Note:** `min` and `max` are accepted but have no functional effect in commercial CheckMK editions (kept for compatibility).

### 3.3 Multiple Metrics

Separate metrics with the pipe character (`|`):

```
count1=42|count2=23
```

On **Windows**, escape the pipe with a circumflex:

```bat
echo 0 "Service" count1=42^|count2=23 Text
```

### 3.4 Dynamic State Calculation (Threshold-based)

Use `P` as the state field instead of a number to let CheckMK compute the state from thresholds:

```
P "My dynamic service" count=40;30;50 Result computed from thresholds
```

The yellow (warn) and red (crit) lines appear in graphs.

You can **alternate** between static and dynamic evaluation in the same script. For example, a backup script:

- Success → use `P` (dynamic state based on duration thresholds):
  ```
  P "Backup job" duration=2342;1800;3600 Successfully created the backup
  ```
- Failure → use a numeric state (`2` = CRIT):
  ```
  2 "Backup job" duration=123;1800;3600 Backup failed. Nuff said.
  ```

### 3.5 Lower and Upper Thresholds (Range-based)

For metrics like humidity that have both lower and upper bounds:

```
metricname=value;warn_low:warn_high;crit_low:crit_high
```

**Example:**
```
P "My service" humidity=37;40:60;30:70 Value is within acceptable range
```
- **WARN** if value < 40 or > 60
- **CRIT** if value < 30 or > 70

To specify only **lower** thresholds (value becomes WARN if *below* a value):
```
P "My service" count_lower=37;40:;30:
```
- **WARN** if value < 40
- **CRIT** if value < 30

> ⚠️ **Caveat:** CheckMK's graphing system only supports **upper thresholds**. Lower thresholds work for state calculation but are **not displayed** in graphs, Perf-O-Meters, or service performance data.

---

## 4. Multi-line State Details

Embed line breaks in the details text using `\n` (which CheckMK interprets as a newline in the UI):

```
P "My service" humidity=37;40:60;30:70 Line one\nLine two with details
```

## 5. Asynchronous Execution (Caching)

If a script takes a long time, cache its output instead of running it on every agent check.

### 5.1 Linux / Unix

Create a numbered subdirectory (seconds between executions) inside the local check directory:

```bash
# Execute this script every 600 seconds (10 minutes):
/usr/lib/check_mk_agent/local/600/mylocalcheck
```

Cached data is written to `/var/lib/check_mk_agent/cache/`.

The service view will display cache information (Unix timestamp and interval).

### 5.2 Windows

Set caching in `C:\ProgramData\checkmk\agent\check_mk.user.yml`:

```yaml
local:
    enabled: yes
    execution:
        - pattern: $CUSTOM_LOCAL_PATH$\mylocalcheck.bat
          async: yes
          run: yes
          cache_age: 600
```

| Key | Description |
|---|---|
| `async` | Whether to cache output |
| `run` | Whether to execute the script |
| `cache_age` | Cache duration in seconds |

> ⚠️ **Platform support:** Caching is available for AIX, FreeBSD, Linux, OpenWrt, and Windows only. On other platforms, use cron jobs with spool directories.

## 6. Distribution via the Agent Bakery (Commercial Editions)

1. As the site user, create your package directory:
   ```bash
   cd ~/local/share/check_mk/agents
   mkdir -p custom/mycustompackage/lib/local/
   ```

2. Place your scripts inside `mycustompackage/lib/local/` (or `mycustompackage/lib/local/600/` for cached scripts on Linux).

3. In CheckMK GUI: Open **Setup → Agents → Windows, Linux, Solaris, AIX → Create → Agent rules → Generic agent options → Deploy custom files with agent** and select your package.

4. CheckMK integrates the package into the agent installation. Bake and distribute.

On Windows, use the rule sets under **Agent rules > Windows agent options**:
- "Set execution mode for plug-ins and local checks"
- "Set cache age for plug-ins and local checks"

## 7. Error Analysis & Troubleshooting

### Check List

| Question | Details |
|---|---|
| **Is the script in the correct directory?** | Verify against the paths below |
| **Are permissions correct?** | Script must be executable; the agent runs as root or LocalSystem |
| **Does the output conform to the syntax?** | Invalid output may be silently ignored (pre-2.4.0p5) or produce a CRIT service (2.4.0p5+) |
| **Environment differences?** | Running the script in a shell differs from running under the agent controller. On Windows, LocalSystem may lack permissions a normal user has |

### 7.1 Test Agent Output on the Target Host

**Linux:**
```bash
cmk-agent-ctl dump | grep -v grep | grep -A2 "<<<<local"
```
Cached entries show `cached(timestamp,interval)` before the data.

**Windows (PowerShell):**
```powershell
./cmk-agent-ctl.exe dump | Select-String "<<<<local" -Context 2
```

### 7.2 Test on the CheckMK Server

**Service discovery:**
```bash
cmk -IIv --detect-plugins=local mycmkserver
```

**Output processing:**
```bash
cmk -nv --detect-plugins=local mycmkserver
```

### 7.3 Windows Character Set Gotcha

Windows agents often produce **UTF-16** output with CR+LF line breaks, but CheckMK expects **UTF-8** with simple LF (`\n`). If you get parse errors, ensure your Windows scripts output UTF-8 with LF line endings. See the spool directory documentation for more details.

## 8. File & Directory Reference

### 8.1 Script Directories (on the target host)

| Operating System | Path |
|---|---|
| **AIX / Linux / Solaris** | `/usr/lib/check_mk_agent/local/` |
| **Windows** | `%ProgramData%\checkmk\agent\local` |

### 8.2 Cache Directory

| Operating System | Path |
|---|---|
| **AIX / Linux / Solaris** | `/var/lib/check_mk_agent/cache/` |

### 8.3 Agent Bakery Paths (on the CheckMK server)

| Purpose | Path |
|---|---|
| Custom agent packages | `~/local/share/check_mk/agents/custom/` |
| Agent cache | `/var/lib/check_mk_agent/cache/` |

## Quick-Start Cheat Sheet

```bash
#!/bin/bash
# Local check: uptime and load in one go

UPTIME=$(uptime -s | wc -l)          # simplified placeholder
LOAD=$(cat /proc/loadavg | awk '{print $1}')

# Service 1: uptime status
echo "0 \"System Uptime\" uptime=$UPTIME System is up"

# Service 2: load average (dynamic state using thresholds)
echo "P \"CPU Load\" load=${LOAD};1.0;2.0;0;10 System load is"
```

Place in `/usr/lib/check_mk_agent/local/`, `chmod +x`, run discovery in CheckMK GUI.

---

## Key Takeaways

1. **The output format is everything** — match the 4-part format exactly.
2. **Use `P` for dynamic state** when you want CheckMK to evaluate thresholds against your values.
3. **Each line = one service** — produce multiple lines for multiple services.
4. **Use caching** (numbered subdirs on Linux, config on Windows) for slow scripts.
5. **Agent Bakery** is the preferred distribution method in commercial editions.
6. **Always test** with `cmk-agent-ctl dump` on the target host and `cmk -nv` on the server before deploying.
7. **Watch out for Windows** character encoding (UTF-16 vs UTF-8) and pipe escaping.
